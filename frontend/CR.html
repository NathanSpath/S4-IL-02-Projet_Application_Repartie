1. Architecture Générale du Système

Notre application repose sur une architecture multiniveau (N-Tier) distribuée permettant de collecter, centraliser et afficher de manière homogène des données de la métropole de Nancy. Les échanges s'articulent autour d'un client léger (navigateur), d'un serveur Proxy intermédiaire gérant les restrictions réseaux (CORS) et d'un écosystème d'objets distants distribués via RMI (Remote Method Invocation) connectés à une base de données relationnelle.

2. État d'Avancement du Projet

Ce qui a été réalisé et validé :

  • Base de données relationnelle : Conception et implémentation du schéma relationnel complet sous Oracle (Tables des restaurants, des tables physiques, des clients et des réservations avec clés étrangères et intégrité référentielle en cascade). Un jeu de données représentatif positionné sur Nancy a été injecté.
  • Infrastructure RMI : Mise en place du Serveur Central faisant office de distributeur et d'annuaire, couplé à l'implémentation dynamique du service de gestion des restaurants (récupération sérialisée en JSON via Jackson et algorithme natif de détection automatique des conflits temporels lors des réservations).
  • Serveur Proxy (HttpServer) : Établissement complet des points d'accès (endpoints) HTTP pour encapsuler les appels. Le proxy résout de manière transparente les requêtes d'incidents routiers en interrogeant les flux OpenData du Grand Nancy via HttpClient, tout en gérant de façon adaptative le cache de l'IUT.
  • Cartographie Client : Initialisation de la carte Leaflet.js centrée sur Nancy avec affichage temps réel, icônes et popups détaillés pour l'ensemble des stations VélOstan'lib (via appel direct HTTPS JCDecaux) et des incidents routiers (via tunnel proxy).

3. Guide de Déploiement et d'Exécution

Pour déployer et exécuter l'application sur les machines de l'IUT ou dans un environnement Linux local, veuillez suivre rigoureusement les étapes d'instanciation ordonnées ci-dessous :

Étape 1 : Initialisation de la base de données

Exécutez le script SQL d'initialisation sur la base de données Oracle de l'IUT afin de structurer les tables et d'accorder les privilèges d'accès requis :

sqlplus e54916u/MotDePasse@charlemagne.iutnc.univ-lorraine.fr:1521/infodb @RMI/sql/setup.sql

Étape 2 : Lancement de l'infrastructure RMI

Démarrez d'abord le registre RMI et le service centralisé de distribution sur la machine hôte principale :

java RMI.launcher.LancerServiceCentral

Sur la même machine ou sur une machine distincte du réseau, démarrez le service de gestion de restaurant en lui fournissant l'adresse IP du serveur centralisé :

java RMI.launcher.LancerServiceRestaurant <IP_SERVEUR_CENTRAL>

Étape 3 : Lancement du Serveur Proxy HTTP

Compilez et démarrez le serveur proxy Java qui va ouvrir le port d'écoute 8080 et lier les différents gestionnaires de requêtes (Handlers) :

java main.ServeurProxy

4. Analyse Critique et Sécurité : Le Contournement du CORS

Dans le cadre de cette SAÉ, nous avons configuré notre serveur proxy pour injecter explicitement l'en-tête de contrôle d'accès "Access-Control-Allow-Origin: *" lors du traitement des requêtes HTTP entrantes provenant du navigateur.

Est-ce une pratique responsable ?

D'un point de vue de la sécurité informatique, l'utilisation de la directive joker * n'est pas idéale en environnement de production, bien qu'elle s'avère pratique en phase de développement local. En configurant l'origine sur *, la protection SOP (Same-Origin Policy) du navigateur est assouplie. Une approche de développement sécurisée consisterait à restreindre cet en-tête en remplaçant l'étoile par l'URL exacte du serveur web autorisé à consommer ces API.
